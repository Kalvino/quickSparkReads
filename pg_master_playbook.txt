## Complete PostgreSQL Master Playbook (Ubuntu 24.04 / 26.04)
This turnkey playbook provides the exact, production-ready execution steps to provision a secure, auditable PostgreSQL environment from scratch. It includes Vector Embeddings (pgvector), granular Access Control Lists (ACLs), optimized indexes, and explicit forensic auditing (pgaudit).
------------------------------
## Step 1: Install PostgreSQL, pgvector, and pgaudit
Run these commands in your Ubuntu terminal to update package repositories and install the database engine along with its advanced extension modules.


# Update system repositories
sudo apt update

# Install PostgreSQL, contrib modules, pgvector, and pgaudit
# Note: Replace "16" with your specific active version if different (e.g., 15 or 17)
sudo apt install -y postgresql-16 postgresql-16-pgvector postgresql-16-pgaudit

# Verify the system daemon is running cleanly
sudo systemctl status postgresql

------------------------------
## Step 2: System Configuration (pgaudit & Password Enforcement)
We must modify global engine configurations to preload security libraries and modify 
the network layer to block unauthenticated password bypasses.
## 1. Configure Engine Memory Layout
Open the primary configuration file using sudo nano:

sudo nano /etc/postgresql/16/main/postgresql.conf

Find, uncomment, or append the following configurations to enforce structured logging 
and preload extension binaries:

shared_preload_libraries = 'pgaudit'
log_statement = 'ddl'
log_line_prefix = '%m [%p] user=%u role=%r db=%d '
pgaudit.log = 'ddl, role'
pgaudit.log_client = off

Save and close (Ctrl+O, then Ctrl+X).
	
## 2. Restrict Authentication Layer (pg_hba.conf)
Open the Host-Based Authentication configuration file:

sudo nano /etc/postgresql/18/main/pg_hba.conf

Scroll to the bottom active lines. Modify the METHOD columns for local and loopback 
configurations to reject unverified empty entries and enforce modern cryptographic 
password checks:

# TYPE  DATABASE        USER            ADDRESS                 METHOD
local   all             postgres                                peer
local   all             all                                     scram-sha-256
host    all             all             127.0.0.1/32            scram-sha-256
host    all             all             ::1/128                 scram-sha-256

Save and close.

## 3. Complete Cold Restart
Because we altered system memory configurations by preloading libraries, a 
configuration reload is insufficient. Execute a complete service reboot:

sudo systemctl restart postgresql

## Step 3: Global Database Automation Blueprint (template1)
To guarantee that every future database created automatically inherits pgvector and 
pgaudit capabilities without manual intervention, register them within the root template 
blueprint database.

# Log into the master template system database as the root daemon user
sudo -u postgres psql -d template1

Run these SQL installation statements inside the prompt:

-- Register extensions to the global template
CREATE EXTENSION IF NOT EXISTS pgvector;
CREATE EXTENSION IF NOT EXISTS pgaudit;

-- Verify extension registration
\dx

-- Safely exit the prompt
\q

## Step 4: The Database Admin & Access Control Playbook
Log in to the primary administration space to build structural isolation containers, roles, 
and object schemas.

sudo -u postgres psql

Execute this complete administrative block sequentially:

-- ============================================================================
-- 1. DATABASE MANIPULATION (CREATE / DROP)
-- ============================================================================
-- Drop database if an old matching test instance exists
DROP DATABASE IF EXISTS ai_project;

-- Create a pristine database instance (automatically clones template1 attributes)
CREATE DATABASE ai_project;

-- ============================================================================
-- 2. USER AND GROUP ROLE MANAGEMENT (CREATE / GRANT / REVOKE)
-- ============================================================================
-- Create un-loggable group container roles (acting as security privilege buckets)
CREATE ROLE project_owners;
CREATE ROLE project_analysts;

-- Create physical human or app user accounts with secure login passwords
CREATE ROLE kal WITH LOGIN SUPERUSER PASSWORD 'Vault_Secure_Admin_2026!';
CREATE ROLE app_backend WITH LOGIN PASSWORD 'App_Engine_ReadWrite_2026!';
CREATE ROLE reporting_user WITH LOGIN PASSWORD 'Analyst_ReadOnly_2026!';

-- Assign users to their respective security group buckets
GRANT project_owners TO app_backend;
GRANT project_analysts TO reporting_user;

-- Demonstration of revoking/scaling back membership
-- GRANT project_owners TO reporting_user; -- (Example mistake allocation)
-- REVOKE project_owners FROM reporting_user; -- (Instantly strips away access)

-- Shift absolute ownership of the core database container to the master group
ALTER DATABASE ai_project OWNER TO project_owners;

-- ============================================================================
-- 3. SCHEMA ACQUISITION & WORKSPACE NAVIGATION
-- ============================================================================
-- Jump directly into the context of our active application database
\c ai_project

-- Register local extensions explicitly if not inherited from template
CREATE EXTENSION IF NOT EXISTS pgvector;
CREATE EXTENSION IF NOT EXISTS pgaudit;

-- Establish Granular Access Rules for the Read-Only Analytics Group
GRANT CONNECT ON DATABASE ai_project TO project_analysts;
GRANT USAGE ON SCHEMA public TO project_analysts;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO project_analysts;
GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO project_analysts;

-- Secure the "New Table Trap" via automation parameters
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO project_analysts;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON SEQUENCES TO project_analysts;

## Step 5: Data Definition Language (DDL) Workspace Playbook
With permissions wired up, we execute the creation and structural formatting of tables, 
specialized vector embedding indexes, and secure system abstraction views.

-- ============================================================================
-- 1. STRUCTURAL DATA DESIGN (CREATE / DROP TABLES)
-- ============================================================================
DROP TABLE IF EXISTS document_embeddings CASCADE;
CREATE TABLE document_embeddings (
    id SERIAL PRIMARY KEY,
    document_title TEXT NOT NULL,
    raw_content TEXT NOT NULL,
    -- vector(3) creates a 3-dimensional floating point floating-array embedding space
    embedding_vector vector(3) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- ============================================================================
-- 2. PERFORMANCE OPTIMIZATION (INDEX DESIGN)
-- ============================================================================
-- Standard B-Tree index optimized for exact matches or range lookups on text keys
CREATE INDEX idx_doc_title ON document_embeddings (document_title);

-- HNSW Vector Index optimized for fast approximate nearest neighbor (ANN) cosine distance searches
-- m=16, ef_construction=64 represent standard baseline accuracy parameters
CREATE INDEX idx_vector_cosine ON document_embeddings USING hnsw (embedding_vector vector_cosine_ops) 
WITH (m = 16, ef_construction = 64);

-- How to edit an index? In PostgreSQL, you safely replace indexes concurrently to prevent read blocks:
-- CREATE INDEX CONCURRENTLY idx_doc_title_new ON document_embeddings (document_title);
-- DROP INDEX CONCURRENTLY idx_doc_title;

-- ============================================================================
-- 3. LOGICAL SYSTEM ABSTRACTIONS (CREATE / DROP VIEWS)
-- ============================================================================
-- Build a view layer to strip raw text or vectors out for lighter client payload reporting
CREATE OR REPLACE VIEW v_document_metadata AS 
SELECT id, document_title, created_at 
FROM document_embeddings;

## Step 6: Data Manipulation Language (DML) Operational Blueprint
This execution block handles day-to-day data mutation primitives: seeding vector strings, 
computing semantic similarity, modifying cell records, and dropping target partitions.

-- ============================================================================
-- 1. DATA ENTRY PRIMITIVES (INSERT)
-- ============================================================================
-- Vector fields accept structured array formats wrapped inside string anchors
INSERT INTO document_embeddings (document_title, raw_content, embedding_vector) VALUES
('AI Strategy 2026', 'Machine learning roadmap and architecture plans.', '[0.12, 0.89, -0.45]'),
('Cyber Security Protocol', 'Zero-trust infrastructure parameters and access controls.', '[0.78, -0.21, 0.54]'),
('Financial Q2 Audit', 'Spreadsheet indices and revenue metrics.', '[-0.34, 0.41, 0.92]');

-- ============================================================================
-- 2. MATHEMATICAL VECTOR SIMILARITY QUERYING (SELECT)
-- ============================================================================
-- The <=> operator calculates the Cosine Distance. Lower distance equals higher semantic match.
SELECT id, document_title, embedding_vector <=> '[0.10, 0.85, -0.40]' AS cosine_distance 
FROM document_embeddings 
ORDER BY embedding_vector <=> '[0.10, 0.85, -0.40]' LIMIT 1;

-- ============================================================================
-- 3. RECORD MUTATION PRIMITIVES (UPDATE / EDIT)
-- ============================================================================
UPDATE document_embeddings 
SET raw_content = 'Updated zero-trust corporate infrastructure policies.', 
    embedding_vector = '[0.79, -0.20, 0.56]' 
WHERE document_title = 'Cyber Security Protocol';

-- ============================================================================
-- 4. FORENSIC PURGING (DELETE)
-- ============================================================================
DELETE FROM document_embeddings 
WHERE created_at < NOW() - INTERVAL '1 year';
